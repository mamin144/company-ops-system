# Phase 14B — الوثيقة 06: الأمان والاسترجاع والتصميم التشغيلي

> **حدود هذا المستند:** تصميم فقط (O10) — **لا تنفيذ**، لا تشغيل نسخ/استرجاع، لا تغيير إعدادات إنتاج، لا تعديل auth. **المراجعة الأمنية لا تضمن الأمان** — هي تقلل الثغرات المكتشفة بالتصميم.
> **الأساس المُدقق:** عقود الجلسة من `session.ts` [Verified] + نموذج الصلاحيات O13 [Confirmed].

---

## 1. أمان المصادقة والجلسة

### 1.1 الحالي (مُدقق) [Confirmed]
- Access token: JWT قصير العمر في الذاكرة + sessionStorage (لا localStorage دائم) [Verified].
- Refresh: cookie `cos_refresh` — HttpOnly، path=/api/auth [Verified] (SameSite/Secure: من الخصائص المعلنة HttpOnly؛ **[Unknown] قيم SameSite/Secure الفعلية — تُثبت عند المراجعة؛ التصميم يتطلب SameSite=Strict/Secure=true** [Proposed]).
- الخروج يلغي جلسة الجهاز الحالي فقط [Verified] — بقية الأجهزة تبقى (سلوك مقصود).
- permissions خلفية دائمًا [Verified].

### 1.2 التعزيزات التصميمية [Proposed]
- TTL قصير للـ access (≤15 دقيقة) مع تجديد صامت عبر refresh؛ تدوير refresh token عند كل استخدام (reuse detection) [Proposed].
- قائمة جلسات المستخدم (عرض/إلغاء جهاز محدد) — إدارية [Proposed لاحقًا، غير ضروري الآن].
- قفل حساب مؤقت بعد N محاولات فاشلة (نافذة زمنية + 429) — N/النافذة قيم تشغيلية (مقترح: 5/15د) [Proposed].
- رسالة فشل الدخول عامة (لا تكشف وجود username) [Proposed — يتوافق مع السلوك البنيوي].
- خروج القسري الجماعي (جميع الأجهزة) عند إعادة تعيين كلمة مرور أو تعطيل حساب [Proposed].

## 2. فرض التخويل (Authorization Enforcement)

- **مبدأ:** كل نقطة API تتحقق ذاتيًا: مصادقة → صلاحية عامة → نطاق مشروع → ملكية/حالة. لا يثق الخادم بأي مرجع من العميل (لا id قائمة مخفية، لا صلاحية معلنة) [Proposed تطبيقاً — نموذج Confirmed].
- خوارزمية الطبقات كما في 05 §4 — **DENY يتقدم**؛ الحساب مركزي (مُحلّل واحد) لا يتكرر لكل نقطة [Proposed — منع التفاوت].
- **فشل التخويل على كتابة حرجة يُسجل تدقيقيًا** (actor, action, resource) — نموذج إشارة استطلاع [Proposed].
- نطاق القوائم (مشاريع/مستندات/تدقيق/بحث) يُطبق في الاستعلام نفسه (شرط JOIN/WHERE) — لا فلترة بعد الجلب [Proposed — مقاطع O9].
- IDOR: كل وصول بعنصر بالمعرف يمر بنفس بوابة النطاق (لا استثناءات للـ GET التفصيلي) [Proposed].

## 3. إعادة تعيين كلمة المرور (O10) — دورة حياة الرمز

| الخاصية | القاعدة التصميمية | التصنيف |

| الاستخدام | **أحادي الاستخدام** (used_at يمنع التكرار) — الاستهلاك ضمن نفس معاملة تغيير الكلمة | [Proposed] |

| التسليم | قناة خارج النطاق التطبيقي: بريد (SMTP) أو تسليم إداري مُوثق — **[Unknown: بنية الإرسال غير موجودة/مثبتة]** → قرار تشغيلي لاحق؛ التصميم لا يفترض بريدًا | [Unknown + تصميم محايد] |

## 4. سلامة التدقيق (Audit Integrity)

- **append-only:** لا API تحديث/حذف؛ الصلاحيات DB لا تشمل UPDATE/DELETE على audit_logs لأي دور [Proposed].
- الكتابة ضمن **نفس المعاملة** لعملية الأعمال (فشل واحد يفشل الاثنين) [Proposed — INT-3].
- لقطة username مع userId (يبقى المعنى بعد تغيّر الأسماء) [Confirmed بنيويًا].
- إخفاء الحقول الحساسة من oldValue/newValue (passwordHash، رموز) [Proposed].
- **تقطيع اختياري مستقبلاً (hash-chaining) لكل سجل** — يُذكر كتحسين لاحق [Proposed — خارج النطاق الحالي].
- استبقاء: غير محدود افتراضيًا (قواعد الاحتفاظ غير معرّفة من المالك — O6-مجاور) [Unknown سياسة].

## 5. منع تسريب البحث (O9)

- البحث ينفذ خلفيًا، وكل مصدر (مشاريع/مستندات) يُستعلم **بشرط النطاق** في SQL/ORM (join على projectAccess) [Proposed].
- **قواعد التسريب المحظورة:** (1) عدد نتائج مجموعة غير مصرح يظهر 0 وليس إجماليًا مخفيًا؛ (2) لا عنوان/مقتطف/معرف/تاريخ لعنصر غير مصرح؛ (3) لا توقيت (timing) قابل للاستنتاج — استعلامات موحدة القياس تقريبًا [Proposed — قيد جودة].
- الفلترة العميلية **غير معتمدة** كضمانة [Confirmed O9] — العميل يعرض ما وصل فقط.
- مقتطفات المستندات (snippets): تُولد فقط من محتوى مُصرح؛ مستند بمشروع NONE لا يظهر إطلاقًا [Proposed].

## 6. النسخ الاحتياطي (O10 — تصميم)

### 6.1 الإنشاء [Proposed]
- أداة: `pg_dump` بتنسيق custom (-Fc) لقاعدة البيانات + نسخة دليل الملفات المرفوعة (documents filePath) — **نسختان متناسقتان كنقطة زمنية** (snapshot label) أو تسلسل موثق [Proposed].
- ملفات DB خارج DB (لا BLOB في القاعدة) — جدول backups ميتاداتا فقط [Proposed].
- checkpoint يتطلب صلاحية تشغيلية (مستخدم خدمة مخصص) — لا يُنفذ من واجهة عادية [Proposed].
- تشغيل تلقائي مجدول (يومي) + يدوي — الجدولة قيمة تشغيلية (مقترح يومي + أسبوعي محفوظ 4 أسابيع) [Proposed قيم].

### 6.2 التخزين والوصول [Proposed]
- مكان: وحدة تخزين خارج خادم التطبيق (دليل مخصص/محرك منفصل/تخزين سحابي لاحقًا) — **ليس داخل دليل الويب القابل للتقديم** [Proposed].
- أذونات OS: مالك الخدمة فقط (no world-read) [Proposed].
- التشفير: إيقاف-at-rest يُفضَّل (مفتاح خارج النسخة) [Proposed — قيمة تشغيلية].
- الوصول عبر API: `backup.manage` [Confirmed المفتاح] فقط؛ التنزيل عبر المسار الإداري المباشر لا endpoint عام للملف [Proposed].
- تسمية موحدة: `cos_backup_YYYYMMDD_HHMMSS_pg.dump` + `..._files.tar` + `manifest.json` (checksums, dbVersion, rowCounts-ملخص) [Proposed].

### 6.3 التحقق من السلامة [Proposed]
- بعد الإنشاء: احتساب SHA-256 لكل ملف + مقارنة manifest + `pg_restore --list` قراءة بنية (دون تنفيذ) → status=verified.
- فحص دوري (أسبوعي [Proposed]) يعيد التحقق على آخر نسخة — تنبيه عند فشل.
- **اختبار استرجاع دوري على بيئة معزولة** (شهرية [Proposed]) — النسخة غير المُختبرة غير موثوقة [مبدأ].

## 7. الاسترجاع (O10) — من خطوتين

1. **dry-run إلزامي:** `restore {mode:'dry-run'}` → تقرير validation_report: checksums، توافق إصدار PG، أعداد صفوف متوقعة، تعارضات (بيانات أحدث موجودة)، حجم التأثير → status=validated. لا يلمس البيانات [Proposed].
2. **commit مقيد:** `restore {mode:'commit', confirmToken}` — يتطلب: dry-run ناجح حديث (≤24سا [Proposed]) + توكن تأكيد يُولد من نتيجة الـ dry-run (يربط الاثنين، يمنع تنفيذًا أعمى) + **قفل كتابة قصير** (maintenance window) أثناء التشغيل [Proposed].
- الاسترجاع يستبدل الحالة بآخر النسخة — **إعلان فقدان الفارق الزمني** إلزامي في التقرير [Proposed].
- تدقيق كامل: restore.requested / dry_run_result / commit_started / commit_completed / failed [Proposed].
- post-restore: فحص سلامة سريع (عدادات حيوية + دخول admin) قبل فتح الخدمة [Proposed].

### 7.1 إجراءات الاسترجاع (RTO/RPO) [Proposed قيم]
- RPO = تكرار النسخ (يومي → ≤24 سا)؛ RTO هدف ≤ 2 سا [Proposed — يُعتمد تشغيليًا].
- خطوات موثقة: (1) إيقاف الكتابة (2) dry-run (3) commit (4) فحص (5) فتح (6) تقرير حادثة.

### 7.2 معايير القبول (Recovery Evidence) [Proposed]
نجاح الاسترجاع = (1) checksums متطابقة (2) بنية قاعدة مقروءة (3) عدد صفوف منطقي مقابل manifest (4) تسجيل دخول admin نجح (5) عينة قراءة من كل موديول (6) تقرير restore_job بحالة completed.

### 7.3 سيناريوهات الفشل التشغيلية [Proposed]
| سيناريو | استجابة التصميم |
|---|---|
| فشل checksum | status=failed؛ إنشاء نسخة جديدة فورًا؛ تنبيه |
| مساحة تخزين ممتلئة | منع إنشاء بفشل صريح (لا استبدال صامت) + تنبيه |
| نسخة أثناء عملية كتابة | أداة dump متسقة (custom format)؛ الجدولة خارج ساعات الذروة [Proposed] |
| استرجاع على قاعدة أحدث | dry-run يكشف التعارضات — قرار المالك قبل commit |
| تعطل أثناء commit | المعاملة/الإجراء قابلة لإعادة التشغيل من آخر checkpoint موثق؛ restore_job=failed موثق |
| فشل القناة (بريد) للرموز | مسار التسليم الإداري المُوثق البديل |
